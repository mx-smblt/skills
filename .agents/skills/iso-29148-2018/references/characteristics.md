# Характеристики вимог — детальні критерії

Цей файл містить розгорнуті критерії для оцінки вимог. Читай його, коли потрібне глибше обґрунтування дефекту або повний аналіз набору вимог. Швидкі перевірки вже є у таблицях SKILL.md — сюди йди за деталями.

## Конструкт well-formed requirement (ISO 29148, 5.2.4)

Добре сформована вимога:

- має чіткий **subject** — хто або що виконує дію (система, сервіс, компонент);
- містить обов'язкову дію через **shall** або узгоджений локальний еквівалент (`повинен`, `має`);
- описує **що** потрібно, а не **як** це реалізувати;
- обмежена умовами (conditions) або constraints, якщо вони потрібні;
- може бути перевірена (є observable outcome);
- описує capability системи, а не користувача;
- не містить зайвих design-рішень, якщо вони не є зовнішнім constraint.

Рекомендовані шаблони (ISO 29148, 5.2.4 та патерни EARS):

- **Event-driven:** `Коли [Умова-подія], [Суб'єкт] повинен [Дія] [Об'єкт] [Обмеження дії]`
- **State-driven:** `Поки [Стан/Режим], [Суб'єкт] повинен [Дія] [Об'єкт] [Обмеження дії]`
- **Unwanted behavior (Error case):** `Якщо [Виняткова ситуація/Помилка], то [Суб'єкт] повинен [Дія] [Об'єкт]`
- **Optional feature:** `Де [Опціональна можливість включена], [Суб'єкт] повинен [Дія] [Об'єкт]`
- **Ubiquitous:** `[Суб'єкт] повинен [Дія] [Об'єкт] [Обмеження дії]`

Приклад: `Коли отримано валідний запит на реєстрацію файлу, система повинна створити унікальний профіль Document Asset протягом 2 секунд.`

Для україномовних вимог допускай: `Система повинна ...`, `Компонент повинен ...`, `Сервіс повинен ...` — але перевіряй, чи вимога справді обов'язкова, конкретна і верифікована.

## Характеристики окремої вимоги (ISO 29148, 5.2.5)

### Necessary — необхідність

Перевір:

- чи описує вимога справді необхідну capability, characteristic, constraint або quality factor;
- чи не є вона зайвою, застарілою або дублюючою;
- чи зрозуміло, яку stakeholder need вона покриває;
- якщо вимога тимчасова або має період актуальності — чи вказані заплановані строки дії (planned expiration / applicability dates).

Проблемні ознаки: вимога не має очевидної цінності; немає джерела або rationale; дублює іншу вимогу без додаткового змісту; застаріла вимога без визначеного строку дії.

### Appropriate — відповідність рівню абстракції

Перевір:

- чи відповідає вимога рівню документа: BRS, StRS, SyRS або SRS;
- чи не містить надто детальних технічних рішень на високому рівні;
- чи не змішує business, stakeholder, system і software-рівні.

Проблемні ознаки: бізнес-вимога містить назви таблиць, класів, API endpoint або технологій без потреби; системна вимога описує внутрішню реалізацію замість зовнішньої поведінки.

### Unambiguous — однозначність

Перевір:

- чи можна вимогу інтерпретувати лише одним способом;
- чи всі терміни визначені;
- чи немає нечітких займенників: `це`, `він`, `вона`, `вони`, `такий`;
- чи немає порівняльних зворотів без визначеної базової лінії чи метрики;
- чи немає неоднозначних logical-конструкцій.

Проблемні ознаки: `швидко`, `зручно`, `ефективно`, `оптимально`, `приблизно`, `за потреби`, `у разі можливості`, `відповідний`, `коректний` (якщо критерій коректності не визначено), `ключові параметри` (якщо перелік не задано), порівняльні фрази без бази: `краще ніж`, `швидше ніж`, `вищої якості`.

### Complete — повнота окремої вимоги

Перевір:

- чи достатньо інформації, щоб зрозуміти вимогу без зовнішніх припущень;
- чи визначені input/output, умови, обмеження, винятки;
- чи зрозумілий очікуваний результат.

Проблемні ознаки: відсутні умови спрацювання; відсутні критерії успіху; не визначено формат, діапазон, одиниці вимірювання; вимога обривається або граматично незавершена.

### Singular — атомарність

Перевір:

- чи описує вимога одну capability, characteristic, constraint або quality factor;
- чи немає кількох незалежних вимог/дій в одному реченні.

Зверни увагу (ISO 29148, 5.2.5 Note 2): вимога може мати кілька одночасних або альтернативних умов (conditions), але повинна визначати одну дію/функцію (action/outcome). Сполучники `і`, `та`, `або` в блоці [Умова] не порушують атомарність, якщо дія системи єдина.

Проблемні ознаки: кілька дієслів/дій в одному положенні (`створити, зберегти та повідомити...`); різні сценарії поведінки в одному пункті без розділення.

Якщо вимога не singular — запропонуй розбити її на кілька незалежних вимог.

### Feasible — здійсненність

Перевір:

- чи виглядає вимога реалізовною в межах відомих constraints;
- чи не потребує неможливих гарантій;
- чи не містить абсолютів без обґрунтування.

Проблемні ознаки: `завжди`, `ніколи`, `усі`, `100%`, `миттєво`, `без обмежень`, `безстроково` (якщо не визначені legal/data retention constraints).

### Verifiable — верифікованість

Перевір:

- чи можна довести виконання вимоги inspection, analysis, demonstration або test;
- чи є вимірювані критерії;
- чи можна написати acceptance criteria або test case.

Проблемні ознаки: неможливо визначити pass/fail; немає метрики; результат суб'єктивний; немає очікуваного observable outcome.

### Correct — коректність

Перевір:

- чи відповідає вимога заявленій stakeholder/business need;
- чи немає суперечності з іншими вимогами;
- чи не підміняє потребу припущенням аналітика.

### Conforming — відповідність стилю

Перевір:

- чи має вимога ID;
- чи відповідає узгодженому шаблону;
- чи використовує єдину термінологію;
- чи має належний рівень формальності.

## Характеристики набору вимог (ISO 29148, 5.2.6)

### Complete — повнота набору

Перевір, чи набір вимог покриває: functional; performance; interface; usability; security; data; operational modes and states; error handling; edge cases; assumptions and dependencies; constraints.

Окремо шукай маркери неповноти: `TBD`, `TBR`, `TBS`, `уточнити`, `пізніше`, `буде визначено`, `за домовленістю`, `ключові параметри` (якщо не перелічені), посилання на неіснуючі або невизначені матриці, таблиці, правила.

### Consistent — узгодженість

Перевір: чи немає конфліктів між вимогами; чи однакові терміни мають однакове значення; чи одиниці виміру й формати даних уніфіковані; чи немає дублювання або overlap.

### Feasible — здійсненність набору

Перевір: чи набір вимог виглядає реалізовним разом; чи не конфліктують performance, cost, schedule, security або regulatory constraints; чи немає взаємовиключних вимог.

### Comprehensible — зрозумілість

Перевір: чи документ має зрозумілу структуру; чи читач може зрозуміти scope, context, actors, data, flows і behavior; чи терміни, скорочення та ролі пояснені.

### Able to be validated — придатність до валідації

Перевір: чи можна підтвердити зі stakeholder, що саме такі вимоги описують потрібну систему; чи є зв'язок із бізнес-цілями, stakeholder needs, scenarios або operational concept; чи є критерії приймання.
