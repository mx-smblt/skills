# Приклади дефектів і виправлень

Цей файл містить розгорнуті приклади типових дефектів вимог і їхніх виправлень. Читай його, коли переформулюєш вимоги — приклади показують, як саме перетворювати погану вимогу на добре сформовану.

## Приклад 1 — невимірювана вимога (Verifiable)

Погано:

```
Система повинна швидко обробляти запити.
```

Проблема: `швидко` не має вимірюваного критерію; вимога не є verifiable.

Краще:

```
Система повинна обробляти 95% запитів на реєстрацію файлу не довше ніж за 2 секунди при навантаженні до 100 запитів на секунду.
```

Якщо поріг невідомий — не вигадуй, постав питання: `Який цільовий час відгуку і навантаження для обробки запитів?`

## Приклад 2 — неатомарна вимога (Singular)

Погано:

```
Система повинна створювати профіль, зберігати файл і повідомляти користувача.
```

Проблема: одна вимога містить три незалежні дії.

Краще (розбити на три):

```
Система повинна створювати унікальний профіль Document Asset для кожного валідного запиту на реєстрацію.

Система повинна зберігати файл, пов'язаний із профілем Document Asset, після успішної реєстрації.

Система повинна повідомляти ініціатора запиту про результат реєстрації профілю.
```

## Приклад 3 — неоднозначний термін (Unambiguous)

Погано:

```
Система повинна порівнювати файл за ключовими параметрами.
```

Проблема: `ключові параметри` не визначені; неможливо створити тест.

Краще:

```
Система повинна вважати файл ідентичним до наявного, якщо збігаються SHA-256 хеш файлу, розмір файлу в байтах і MIME-тип.
```

Якщо параметри невідомі, постав питання: `Які саме параметри вважаються ключовими для порівняння файлів: hash, file name, size, MIME-type, metadata або інші?`

## Приклад 4 — приховане design-рішення (Appropriate)

Погано:

```
Система повинна зберігати профілі в PostgreSQL.
```

Проблема: це design constraint або архітектурне рішення, а не функціональна вимога, якщо PostgreSQL не є зовнішнім обмеженням.

Краще як constraint:

```
Система повинна використовувати PostgreSQL як сховище профілів Document Asset відповідно до затвердженого архітектурного рішення ADR-[ID].
```

Або як функціональна вимога без design-рішення:

```
Система повинна зберігати профілі Document Asset так, щоб вони були доступні для подальшого пошуку за унікальним ідентифікатором профілю.
```

## Приклад 5 — user story без acceptance criteria (Complete/Verifiable)

Погано:

```
Як користувач, я хочу завантажувати файли, щоб зберігати документи.
```

Проблема: user story без acceptance criteria не є verifiable; `завантажувати файли` не визначає типи, розміри, обмеження.

Краще (story + acceptance criteria):

```
Як користувач, я хочу завантажувати документи, щоб зберігати їх у сховищі.

Acceptance criteria:
- Система повинна приймати файли з MIME-типами PDF, DOCX, XLSX.
- Система повинна відхиляти файл із розміром понад 50 МБ і показувати повідомлення про помилку.
- Після успішного завантаження система повинна показувати ідентифікатор документа.
```

## Приклад 6 — негативне формулювання (language)

Погано:

```
Система не повинна дозволяти доступ неавторизованим користувачам.
```

Проблема: подвійна негативність ускладнює перевірку; не описує, що система має робити.

Краще:

```
Система повинна надавати доступ до документа лише користувачам, які пройшли аутентифікацію і мають роль з правом доступу до відповідного профілю.
```

## Приклад 7 — обов'язковість через `має можливість` (language)

Погано:

```
Система має можливість експортувати дані.
```

Проблема: `має можливість` — це allowance, а не binding requirement; незрозуміло, чи обов'язковий експорт.

Краще (якщо обов'язково):

```
Система повинна експортувати список документів у форматі CSV за запитом користувача.
```

Краще (якщо опціонально):

```
Система може експортувати список документів у форматі CSV. (опціональна можливість, не є вимогою)
```

## Приклад 8 — пасивний стан (language)

Погано:

```
Повинна виконуватись перевірка підпису запиту.
```

Проблема: пасивний стан не вказує, хто або що виконує дію.

Краще:

```
Система повинна перевіряти підпис запиту перед обробкою запиту.
```

## Приклад 9 — абсолютні терміни без обґрунтування (Feasible)

Погано:

```
Система повинна завжди бути доступною.
```

Проблема: `завжди` неможливо гарантувати; немає метрики availability.

Краще:

```
Система повинна забезпечувати доступність 99.9% часу протягом робочого дня (08:00–18:00 UTC+2).
```

## Приклад 10 — TBD/TBR placeholder (Complete)

Погано:

```
R-042: TBD — визначити правила доступу до документів.
```

Проблема: вимога не завершена; неможливо реалізувати або перевірити.

Краще:

```
R-042: Система повинна надавати доступ до документу лише користувачам, які мають роль 'viewer', 'editor' або 'admin' для відповідного документу.
```

Якщо неможливо завершити — постав питання: `Які ролі та права доступу до документів мають бути підтримані системою?`

## Приклад 11 — порівняльні фрази без бази чи метрики (Unambiguous/Verifiable)

Погано:

```
Система повинна забезпечувати вищу якість стиснення та швидшу обробку файлів, ніж попередня версія.
```

Проблема: `вищу якість` та `швидшу обробку` — comparative phrases без конкретної базової лінії, метрик та умов тестування.

Краще:

```
Система повинна виконувати компресію PDF-документів розміром до 100 МБ зі збереженням коефіцієнта стиснення не менше 30% та тривалістю обробки до 5 секунд.
```

Якщо базова система відома: "Які точні показники часу та коефіцієнта стиснення у версії X є базовими для порівняння?"

## Приклад 12 — складена умова при єдиній дії (Singular — валідна вимога)

Зразок правильної вимоги зі складеною умовою (ISO 29148:2018, 5.2.5 Note 2):

```
Коли користувач має роль 'Auditor' і статус документа є 'Archived', система повинна відкривати документ у режимі лише для читання протягом 1 секунди.
```

Пояснення: вимога містить кілька умов (роль Auditor + статус Archived), але описує одну атомарну дію системи (відкриття у режимі read-only). Така вимога є **Singular** (атомарною).

## Приклад 13 — синергія EARS та Acceptance Criteria (Gherkin / Given-When-Then)

Вимога за синтаксисом EARS (Unwanted Behavior / Complex):

```
У разі наявності модуля аудиту, якщо неавторизований користувач надсилає запит на видалення файлу, то система повинна відхилити запит із кодом HTTP 401 та зафіксувати подію в журналі аудиту безпеки.
```

Трансформація в поведінкові Acceptance Criteria (Given-When-Then):

```gherkin
Scenario: Спроба неавторизованого видалення файлу
  Given у системі активовано модуль безпекового аудиту
  And користувач не пройшов автентифікацію
  When користувач надсилає запит DELETE /documents/12345
  Then система повертає HTTP статус 401 Unauthorized
  And система створює запис у журналі безпеки з типом 'UNAUTHORIZED_DELETION_ATTEMPT'
```

## Приклад 14 — критична вимога безпеки із прямою забороною (Safety Prohibition)

Погано (розмите позитивне формулювання без гарантії блокування):

```
Система повинна забезпечувати безпеку під час перевищення тиску.
```

Проблема: вимога не є верифікованою, відсутній чіткий тригер та конкретна дія системи.

Краще (Safety Prohibition за ISO 29148:2018 5.2.7):

```
Система не повинна відкривати захисний клапан скиду, поки тиск у первинному контурі перевищує 15 бар.
```

Пояснення: конструкція `не повинен` (`shall not`) є стандартизованим винятком для вимог функціональної безпеки, де пряма заборона небезпечного стану є критично важливою.

## Приклад 15 — виправлення антипатернів EARS

Погано (змішування `Якщо` та `Коли` для штатної події + подвійний тригер):

```
Якщо користувач натискає кнопку експорту і якщо звіт сформовано, то система повинна зберегти файл.
```

Проблема:
1. `Якщо` використано для штатної події замість помилки.
2. Подвійний тригер порушує `Singular` (незрозуміло: це подія чи стан).

Краще за EARS (State-driven + Event-driven):

```
Поки звіт перебуває у стані 'Generated', коли користувач надсилає запит на експорт, система повинна надати файл звіту у форматі XLSX протягом 3 секунд.
```
