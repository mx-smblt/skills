# Мова вимог — правила та повні списки

Цей файл містить повні правила мови вимог (ISO 29148, 5.2.7) і повні списки проблемних термінів з прикладами виправлень. Читай його, коли аналізуєш формулювання або переформулюєш вимоги.

## Обов'язковість (modal verbs)

Вимоги мають бути сформульовані як обов'язкові provisions.

| Слово                                 | Значення                                        | Чи є вимогою? |
|---------------------------------------|-------------------------------------------------|---------------|
| `shall` / `повинен`, `має`            | обов'язкова вимога (binding)                    | ✅ так        |
| `should` / `бажано`, `рекомендується` | preference, goal — не обов'язково               | ❌ ні         |
| `may` / `може`, `зможе`               | allowance, дозвіл                               | ❌ ні         |
| `will` / `буде`, `планується`         | факт, майбутнє, контекст                        | ❌ ні         |
| `must` / `треба`                      | неоднозначно — може читатись як вимога або факт | ⚠️ уникай     |

Рекомендовано: `Система повинна ...`

Позначай як дефект і переформулюй: `має можливість`, `слід`, `може`, `буде`, `зможе`, `повинен мати можливість`, `бажано`, `рекомендується`, `можливо`, `планується`.

Пояснюй, що `should`, `may`, `will` або їх локальні еквіваленти описують цілі, припущення або контекст, але не binding requirement.

## Активний стан

Перевага — активний стан:

```
Система повинна перевіряти підпис запиту.
```

Проблемно (пасивний стан):

```
Повинна виконуватись перевірка підпису запиту.
```

## Позитивні формулювання

Перевага — позитивні вимоги.

Проблемно:

```
Система не повинна дозволяти доступ неавторизованим користувачам.
```

Краще:

```
Система повинна надавати доступ до файлу лише користувачам, які мають право доступу до відповідного профілю.
```

*Виняток (ISO 29148, 5.2.7):* Конструкція `не повинен` (`shall not`) допускається виключно для критичних вимог безпеки (Safety/Security Prohibitions), коли необхідно однозначно заборонити небезпечний або аварійний стан системи.

Приклад:
```
Система не повинна відкривати захисний клапан, поки тиск у контурі перевищує 15 бар.
```

## Ключові слова та синтаксис EARS (локалізація)

Методологія EARS (Easy Approach to Requirements Syntax) використовує фіксовані ключові слова для однозначного позначення тригерів, станів, конфігурацій та помилок.

| EARS Keyword | Український відповідник | Патерн EARS | Контекст використання | Приклад |
|---|---|---|---|---|
| *(none)* | `[Суб'єкт] повинен ...` | **Ubiquitous** | Постійна/безумовна дія системи | `Система повинна шифрувати всі збережені профілі за алгоритмом AES-256.` |
| `When` | `Коли [подія-тригер], ...` | **Event-driven** | Дискретна подія, дія користувача, надходження запиту | `Коли користувач надсилає запит на експорт, система повинна згенерувати CSV-файл протягом 3 секунд.` |
| `While` | `Поки [стан/режим], ...` | **State-driven** | Тривалий стан системи або активний режим роботи | `Поки система перебуває у режимі обслуговування, система повинна блокувати нові транзакції.` |
| `Where` | `У разі наявності [модуля/опції], ...` | **Optional feature** | Специфічна апаратна, програмна чи ліцензійна конфігурація | `У разі наявності модуля оптичного розпізнавання, система повинна вилучати текст із завантажених PDF-сканів.` |
| `If ..., then ...` | `Якщо [збій/помилка], то [система] повинна ...` | **Unwanted behavior** | Виняткова ситуація, збій апаратури, невалідні вхідні дані | `Якщо отримано невалідний токен автентифікації, то система повинна відхилити запит з кодом HTTP 401.` |

### Правила застосування ключових слів EARS:
- **Не плутай `Коли` та `Поки`:** `Коли` позначає миттєву подію (тригер), а `Поки` — період перебування у стані чи режимі.
- **Не використовуй `Якщо` для штатних сценаріїв:** Ключове слово `Якщо` (`If ..., then ...`) зарезервовано виключно для обробки помилок, виняткових ситуацій та збоїв (*Unwanted behavior*). Для нормальних бізнес-подій використовуй `Коли` (*Event-driven*).
- **Порядок чергування у складних вимогах (*Complex*):** `У разі наявності [Опції], поки [Стан], коли [Подія], система повинна [Дія]...` (англ. `Where ... while ... when ... the system shall ...`).

## Повні списки розмитих термінів (ISO 29148, 5.2.7)

Позначай як проблему такі класи слів:

- **Суперлативи** (без критерію): `найкращий`, `максимальний`, `мінімальний`, `best`, `most`.
- **Порівняльні фрази** (без базової лінії або метрики): `краще ніж`, `швидше ніж`, `вищої якості`, `покращений`, `better than`, `higher quality`, `superior`.
- **Суб'єктивні слова**: `зручний`, `простий`, `легкий`, `інтуїтивний`, `user friendly`, `easy to use`, `cost effective`.
- **Розмиті прикметники/прислівники**: `швидко`, `часто`, `значний`, `майже завжди`, `almost always`, `minimal`, `significant`.
- **Open-ended expressions**: `тощо`, `і так далі`, `включаючи, але не обмежуючись`, `but not limited to`, `as a minimum`, `provide support`.
- **Loopholes**: `якщо можливо`, `за потреби`, `де застосовно`, `у разі можливості`, `if possible`, `as appropriate`, `as applicable`.
- **Абсолютні терміни** (якщо не обґрунтовані й не верифіковані): `всі`, `кожен`, `завжди`, `ніколи`, `all`, `always`, `never`, `every`.
- **Неповні посилання**: стандарт, документ або матриця без версії, дати або конкретного розділу.
- **Розмиті займенники**: `це`, `він`, `вона`, `вони`, `такий`, `it`, `this`, `that` — заміни на конкретний термін.
- **Неоднозначні логічні конструкції в діях**: `або`, `and/or` (якщо об'єднують кілька дій) — розглядай як кандидатів на розбиття на кілька окремих вимог.

## What, not how (приховані design-рішення)

Вимога описує, **що** потрібно системі, а не **як** це реалізувати.

- Конкретна технологія, архітектура, назва БД чи фреймворку — це design-рішення.
- Якщо воно є **зовнішнім constraint** (накладено регулятором, контрактом, існуючою платформою) — оформи як constraint з посиланням на джерело.
- Якщо воно є внутрішнім рішенням — винеси в атрибут (rationale) або окремий constraint, а не у функціональну вимогу.

Приклад: `Система повинна зберігати профілі в PostgreSQL.` → як constraint: `Система повинна використовувати PostgreSQL відповідно до затвердженого архітектурного рішення ADR-[ID].`
