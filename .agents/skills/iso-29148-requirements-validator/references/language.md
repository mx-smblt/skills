# Мова вимог — правила та повні списки

Цей файл містить повні правила мови вимог (ISO 29148, 5.2.7) і повні списки проблемних термінів з прикладами виправлень. Читай його, коли аналізуєш формулювання або переформулюєш вимоги.

## Обов'язковість (modal verbs)

Вимоги мають бути сформульовані як обов'язкові provisions.

| Слово                                 | Значення                                        | Чи є вимогою? |
|---------------------------------------|-------------------------------------------------|---------------|
| `shall` / `повинен`, `має`            | обов'язкова вимога (binding)                    | ✅ так        |
| `should` / `бажано`, `рекомендується` | preference, goal — не обов'язково               | ❌ ні         |
| `may` / `може`, `зможе`               | allowance, дозвіл                               | ❌ ні         |
| `will` / `буде`, `планується`         | факт, майбутнє, контекст                        | ❌ ні         |
| `must` / `треба`                      | неоднозначно — може читатись як вимога або факт | ⚠️ уникай     |

Рекомендовано: `Система повинна ...`

Позначай як дефект і переформулюй: `має можливість`, `слід`, `може`, `буде`, `зможе`, `повинен мати можливість`, `бажано`, `рекомендується`, `можливо`, `планується`.

Пояснюй, що `should`, `may`, `will` або їх локальні еквіваленти описують цілі, припущення або контекст, але не binding requirement.

## Активний стан

Перевага — активний стан:

```
Система повинна перевіряти підпис запиту.
```

Проблемно (пасивний стан):

```
Повинна виконуватись перевірка підпису запиту.
```

## Позитивні формулювання

Перевага — позитивні вимоги.

Проблемно:

```
Система не повинна дозволяти доступ неавторизованим користувачам.
```

Краще:

```
Система повинна надавати доступ до файлу лише користувачам, які мають право доступу до відповідного профілю.
```

## Повні списки розмитих термінів (ISO 29148, 5.2.7)

Позначай як проблему такі класи слів:

- **Суперлативи** (без критерію): `найкращий`, `максимальний`, `мінімальний`, `best`, `most`.
- **Суб'єктивні слова**: `зручний`, `простий`, `легкий`, `інтуїтивний`, `user friendly`, `easy to use`.
- **Розмиті прикметники/прислівники**: `швидко`, `часто`, `значний`, `майже завжди`, `almost always`.
- **Open-ended expressions**: `тощо`, `і так далі`, `включаючи, але не обмежуючись`, `but not limited to`, `as a minimum`.
- **Loopholes**: `якщо можливо`, `за потреби`, `де застосовно`, `if possible`, `as appropriate`.
- **Абсолютні терміни** (якщо не обґрунтовані й не верифіковані): `всі`, `кожен`, `завжди`, `ніколи`.
- **Неповні посилання**: стандарт, документ або матриця без версії, дати або конкретного розділу.
- **Розмиті займенники**: `це`, `він`, `вона`, `вони`, `такий` — заміни на конкретний термін.
- **Неоднозначні логічні конструкції**: `або`, `and/or` — розглядай як кандидатів на розбиття на кілька вимог.

## What, not how (приховані design-рішення)

Вимога описує, **що** потрібно системі, а не **як** це реалізувати.

- Конкретна технологія, архітектура, назва БД чи фреймворку — це design-рішення.
- Якщо воно є **зовнішнім constraint** (накладено регулятором, контрактом, існуючою платформою) — оформи як constraint з посиланням на джерело.
- Якщо воно є внутрішнім рішенням — винеси в атрибут (rationale) або окремий constraint, а не у функціональну вимогу.

Приклад: `Система повинна зберігати профілі в PostgreSQL.` → як constraint: `Система повинна використовувати PostgreSQL відповідно до затвердженого архітектурного рішення ADR-[ID].`
