# Приклади дефектів і виправлень

Цей файл містить розгорнуті приклади типових дефектів вимог і їхніх виправлень. Читай його, коли переформулюєш вимоги — приклади показують, як саме перетворювати погану вимогу на добре сформовану.

## Приклад 1 — невимірювана вимога (Verifiable)

Погано:

```
Система повинна швидко обробляти запити.
```

Проблема: `швидко` не має вимірюваного критерію; вимога не є verifiable.

Краще:

```
Система повинна обробляти 95% запитів на реєстрацію файлу не довше ніж за 2 секунди при навантаженні до 100 запитів на секунду.
```

Якщо поріг невідомий — не вигадуй, постав питання: `Який цільовий час відгуку і навантаження для обробки запитів?`

## Приклад 2 — неатомарна вимога (Singular)

Погано:

```
Система повинна створювати профіль, зберігати файл і повідомляти користувача.
```

Проблема: одна вимога містить три незалежні дії.

Краще (розбити на три):

```
Система повинна створювати унікальний профіль Document Asset для кожного валідного запиту на реєстрацію.

Система повинна зберігати файл, пов'язаний із профілем Document Asset, після успішної реєстрації.

Система повинна повідомляти ініціатора запиту про результат реєстрації профілю.
```

## Приклад 3 — неоднозначний термін (Unambiguous)

Погано:

```
Система повинна порівнювати файл за ключовими параметрами.
```

Проблема: `ключові параметри` не визначені; неможливо створити тест.

Краще:

```
Система повинна вважати файл ідентичним до наявного, якщо збігаються SHA-256 хеш файлу, розмір файлу в байтах і MIME-тип.
```

Якщо параметри невідомі, постав питання: `Які саме параметри вважаються ключовими для порівняння файлів: hash, file name, size, MIME-type, metadata або інші?`

## Приклад 4 — приховане design-рішення (Appropriate)

Погано:

```
Система повинна зберігати профілі в PostgreSQL.
```

Проблема: це design constraint або архітектурне рішення, а не функціональна вимога, якщо PostgreSQL не є зовнішнім обмеженням.

Краще як constraint:

```
Система повинна використовувати PostgreSQL як сховище профілів Document Asset відповідно до затвердженого архітектурного рішення ADR-[ID].
```

Або як функціональна вимога без design-рішення:

```
Система повинна зберігати профілі Document Asset так, щоб вони були доступні для подальшого пошуку за унікальним ідентифікатором профілю.
```

## Приклад 5 — user story без acceptance criteria (Complete/Verifiable)

Погано:

```
Як користувач, я хочу завантажувати файли, щоб зберігати документи.
```

Проблема: user story без acceptance criteria не є verifiable; `завантажувати файли` не визначає типи, розміри, обмеження.

Краще (story + acceptance criteria):

```
Як користувач, я хочу завантажувати документи, щоб зберігати їх у сховищі.

Acceptance criteria:
- Система повинна приймати файли з MIME-типами PDF, DOCX, XLSX.
- Система повинна відхиляти файл із розміром понад 50 МБ і показувати повідомлення про помилку.
- Після успішного завантаження система повинна показувати ідентифікатор документа.
```

## Приклад 6 — негативне формулювання (language)

Погано:

```
Система не повинна дозволяти доступ неавторизованим користувачам.
```

Проблема: подвійна негативність ускладнює перевірку; не описує, що система має робити.

Краще:

```
Система повинна надавати доступ до документа лише користувачам, які пройшли аутентифікацію і мають роль з правом доступу до відповідного профілю.
```

## Приклад 7 — обов'язковість через `має можливість` (language)

Погано:

```
Система має можливість експортувати дані.
```

Проблема: `має можливість` — це allowance, а не binding requirement; незрозуміло, чи обов'язковий експорт.

Краще (якщо обов'язково):

```
Система повинна експортувати список документів у форматі CSV за запитом користувача.
```

Краще (якщо опціонально):

```
Система може експортувати список документів у форматі CSV. (опціональна можливість, не є вимогою)
```
