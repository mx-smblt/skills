## 1. Відповідність стандарту та адаптація (Clause 2: Conformance & Tailoring)

Згідно з Розділом 2 стандарту ISO/IEC 25010:2011, будь-яка специфікація вимог, архітектура або оцінка якості відповідає стандарту, якщо вона:
1. **Пряме використання:** Безпосередньо використовує моделі якості продукту (4.2) та якості у використанні (4.1); **або**
2. **Адаптація (Tailoring):** Адаптує модель під специфіку домену/проєкту, надаючи:
   - Обґрунтування (rationale) виключення або зміни будь-яких характеристик/підхарактеристик;
   - Матрицю відповідності (mapping) між адаптованою та стандартною моделлю.

*Примітка:* Неможливо виміряти всі 31 підхарактеристику для кожної підсистеми великого продукту. Стандарт заохочує обґрунтовану пріоритизацію характеристик на основі бізнес-цілей стейкхолдерів.

## 2. Рівні відповідності та критичність дефектів (Conformance & Severity)

### Рівні відповідності характеристики / підсистеми (Conformance Status)

| Статус | Позначення | Критерій |
|--------|------------|----------|
| **Full Conformance (Повна відповідність)** | 🟢 CONFORMANT | Вимоги/архітектура/код повністю задовольняють характеристики ISO 25010; наявні вимірювані метрики; критичні та мажорні дефекти відсутні. |
| **Partial Conformance (Часткова відповідність)** | 🟡 PARTIAL | Характеристика частково врахована, але є прогалини (Gaps), недостатня вимірюваність або наявні дефекти рівня Major/Minor. Потрібні доопрацювання. |
| **Non-Conformance (Невідповідність)** | 🔴 NON-CONFORMANT | Характеристика повністю проігнорована або виявлено блокуючі Critical дефекти (ризики втрати даних, безпекові діри, каскадні падіння). |
| **Not Applicable / Tailored out** | ⚪ N/A | Характеристика свідомо виключена в рамках задокументованого tailoring (наприклад, UI Aesthetics для headless CLI утиліти). |

### Рівні критичності дефектів (Severity Matrix)

- 🔴 **Critical:** Дефект або прогалина робить систему непридатною до безпечної експлуатації, порушує базову функціональність, створює загрозу витоку даних чи незворотної втрати цілісності. Блокує реліз.
- 🟠 **Major:** Значне порушення якості або відсутність ключових НФВ (наприклад, відсутність circuit breaker при виклику зовнішніх API, розмиті вимоги до продуктивності, відсутність валідації вводу). Створює високі ризики при навантаженні чи змінах.
- 🟡 **Minor:** Локальний дефект або помірне відхилення від кращих практик (відсутність інтернаціоналізації, незначне дублювання коду, недосконалі повідомлення про помилки).
- 🔵 **Info / Opportunity:** Пропозиція щодо оптимізації або подальшого розвитку (впровадження distributed tracing, підвищення покриття тестів).

## 4. Аналіз компромісів якості (Quality Trade-offs & Balancing)

При розробці рекомендацій щодо покращення обов'язково враховуй взаємний вплив (trade-offs) між характеристиками:

```
┌───────────────────────────────────────┬───────────────────────────────────────┐
│ Підвищення характеристики             │ Можливий негативний вплив (Trade-off) │
├───────────────────────────────────────┼───────────────────────────────────────┤
│ Security (Шифрування, mTLS, аудит)    │ ──► Зниження Performance (Latency/CPU)│
│                                       │ ──► Зниження Usability (MFA, сесії)   │
├───────────────────────────────────────┼───────────────────────────────────────┤
│ Modularity (Мікросервіси, патерни)    │ ──► Збільшення складності діагностики │
│                                       │ ──► Зниження Time Behaviour (Network) │
├───────────────────────────────────────┼───────────────────────────────────────┤
│ Fault tolerance (Реплікація, Retry)   │ ──► Збільшення Resource Utilization   │
│                                       │ ──► Ризик перевантаження (Thundering) │
├───────────────────────────────────────┼───────────────────────────────────────┤
│ Flexibility / Adaptability            │ ──► Збільшення кодової бази           │
│                                       │ ──► Потенційне зниження Testability   │
└───────────────────────────────────────┴───────────────────────────────────────┘
```

**Правило балансування:** Завжди обґрунтовуй запропоноване покращення з точки зору бізнес-пріоритетів та мінімізуй супутні негативні ефекти через компенсаторні заходи (наприклад: апаратне прискорення шифрування, кешування токенів, асинхронне логування аудиту).

## 5. Розробка плану покращення (Remediation & Action Plan)

Для кожної виявленої проблеми формула рекомендації має містити:
1. **Що саме змінити (Specific Change):** Конкретна дія в коді, конфігурації, архітектурі чи вимогах.
2. **Як це перевірити (Verification Method & Metric):** Якою метрикою SQuaRE або тестом підтвердити усунення проблеми.
3. **Очікуваний результат за ISO 25010:** Яка підхарактеристика перейде з 🔴/🟡 в 🟢.

*Приклад рекомендації:*
- **Проблема:** У системі відсутні обмеження на кількість запитів (Capacity / Security -> Availability / Integrity).
- **Покращення:** Впровадити Rate Limiting на API Gateway з використанням алгоритму Token Bucket (ліміт: 100 req/min на IP / користувача) та повертати статус HTTP 429 з заголовком `Retry-After`.
- **Верифікація:** Навантажувальний тест (JMeter/k6) генерує 150 RPS; перевірити отримання 429 помилок для надлишкових запитів та збереження latency < 200ms для легітимного трафіку.
- **Результат ISO 25010:** Підвищення рівня відповідності 4.2.2.3 (Capacity) та 4.2.5.3 (Fault tolerance) до 🟢 CONFORMANT.
