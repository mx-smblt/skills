# Приклади аналізу, звітів та планів покращення (ISO/IEC 25010)

Цей файл містить практичні приклади аналізу вимог, архітектури та систем за стандартом ISO/IEC 25010:2011, а також приклади формування звітів і планів покращення.

---

## Приклад 1: Аудит та переформулювання нефункціональних вимог (NFR)

### Вхідні вимоги (Початковий стан)
> 1. Система повинна бути швидкою та надійною.
> 2. Дані користувачів мають бути повністю захищені від хакерів.
> 3. Додаток повинен працювати скрізь та бути легким у супроводі.

### Результат аналізу за ISO 25010

- **Вимога 1:**
  - *Дефект:* Розмиті терміни `швидкою` та `надійною`. Порушено підхарактеристики **Time behaviour (4.2.2.1)** та **Availability (4.2.5.2)** / **Fault tolerance (4.2.5.3)**. Немає вимірюваних критеріїв. Severity: 🟠 Major.
  - *Покращення (ISO 25010):*
    - `[NFR-PERF-01] Система повинна повертати відповідь на 95% GET-запитів до API пошуку не довше ніж за 200 мс при навантаженні до 500 RPS (Time behaviour).`
    - `[NFR-REL-01] Система повинна забезпечувати коефіцієнт готовності (Availability) не менше 99.9% у режимі 24/7/365, з максимальним часом непланового простою не більше 8.76 годин на рік.`
- **Вимога 2:**
  - *Дефект:* Абсолютне твердження `повністю захищені від хакерів` без конкретизації підхарактеристик безпеки **Confidentiality (4.2.6.1)**, **Integrity (4.2.6.2)**, **Authenticity (4.2.6.5)**. Severity: 🟠 Major.
  - *Покращення (ISO 25010):*
    - `[NFR-SEC-01] Система повинна шифрувати всі персональні дані (PII) у стані спокою за стандартом AES-256 та під час передачі мережею за протоколом TLS 1.3 (Confidentiality).`
    - `[NFR-SEC-02] Система повинна вимагати проходження багатофакторної автентифікації (TOTP/FIDO2) для всіх користувачів з адміністративними привілеями (Authenticity).`
- **Вимога 3:**
  - *Дефект:* Невизначені фрази `працювати скрізь` та `легким у супроводі`. Порушено **Adaptability (4.2.8.1)**, **Modularity (4.2.7.1)**, **Testability (4.2.7.5)**. Severity: 🟠 Major.
  - *Покращення (ISO 25010):*
    - `[NFR-PORT-01] Клієнтська частина додатку повинна коректно функціонувати в браузерах Chrome (>=v110), Safari (>=v16), Firefox (>=v115) та Edge (>=v110) на десктопних і мобільних пристроях (Adaptability).`
    - `[NFR-MAINT-01] Кодова база системи повинна мати модульну архітектуру з покриттям модульними та інтеграційними автотестами не менше 80% рядків коду в CI/CD пайплайні (Testability / Modularity).`

## Приклад 2: Архітектурний GAP-аналіз платіжного шлюзу

### Вхідний опис архітектури
> Мікросервіс обробки платежів на Node.js отримує запити від мобільного додатку, валідує їх та відправляє синхронний HTTP запит до зовнішнього банку-еквайєра. Дані про транзакцію зберігаються в MongoDB. Логи записуються у стандартний stdout без кореляційних ID.

### Звіт GAP-аналізу за ISO 25010

```markdown
# Звіт аудиту архітектури платіжного шлюзу (ISO 25010)

### 1. Зведена таблиця відповідності

| Характеристика якості | Статус | Основні знахідки та ризики |
|-----------------------|--------|----------------------------|
| 1. Functional Suitability | 🟢 CONFORMANT | Базові функції проведення платежу специфіковані. |
| 2. Performance Efficiency | 🟡 PARTIAL | Синхронний виклик еквайєра блокує потік при затримках банку (Time behaviour). |
| 3. Compatibility          | 🟢 CONFORMANT | Використовується стандартний REST JSON API. |
| 4. Usability              | ⚪ N/A | Бекенд-сервіс (Tailored out). |
| 5. Reliability            | 🔴 NON-CONFORMANT | Відсутній Circuit Breaker при падінні банку; немає механізму Retry/Idempotency. |
| 6. Security               | 🔴 NON-CONFORMANT | Відсутні Non-repudiation (підпис транзакцій) та Accountability (немає наскрізного Trace ID). |
| 7. Maintainability        | 🟡 PARTIAL | Неструктуровані логи (stdout) ускладнюють Analysability. |
| 8. Portability            | 🟢 CONFORMANT | Контейнеризовано в Docker. |

### 2. Ключові дефекти (Findings)
- 🔴 **[CRIT-01] Reliability -> Fault tolerance (4.2.5.3):** Синхронне очікування відповіді зовнішнього банку без таймаутів та Circuit Breaker призведе до вичерпання пулу з'єднань Node.js (Cascading Failure) при аварії на стороні банку.
- 🔴 **[CRIT-02] Security -> Non-repudiation & Accountability (4.2.6.3 / 4.2.6.4):** Відсутність HMAC-підпису або цифрового підпису запиту унеможливлює юридичне доведення факту транзакції; відсутність Correlation ID унеможливлює розслідування фінансових інцидентів.
- 🟠 **[MAJ-01] Reliability -> Recoverability (4.2.5.4):** У разі збою мережі під час відповіді банку статус платежу залишається невизначеним без механізму Reconciliation / Outbox pattern.

### 3. План покращення (Remediation Plan)

1. **[QW-1] Впровадження Circuit Breaker та Timeout:**
   - Налаштувати `opossum` або аналог для викликів банку: timeout = 3.5s, відкриття ланцюга після 50% помилок за 10s.
2. **[QW-2] Додавання Correlation ID та структурованого JSON-логування:**
   - Генерувати `X-Correlation-ID` на вході API Gateway і передавати його через усі внутрішні та зовнішні заголовки для забезпечення **Accountability (4.2.6.4)** та **Analysability (4.2.7.3)**.
3. **[ARCH-1] Впровадження патерну Transactional Outbox + Idempotency Key:**
   - Зберігати подію платежу в MongoDB в одній транзакції зі станом, відправляти через RabbitMQ/Kafka, використовувати клієнтський `Idempotency-Key` для виключення дублюючих списань (**Functional correctness 4.2.1.2** & **Economic risk mitigation 4.1.4.1**).
```

## Приклад 3: Оцінка якості у використанні (Quality in Use) медичної системи

### Вхідний сценарій
> Медсестра реанімаційного відділення вводить призначення препарату через планшетний додаток під час екстреної ситуації.

### Оцінка за характеристиками Quality in Use

- **Effectiveness (4.1.1):**
  - *Оцінка:* Помилка вибору дозування через занадто дрібні радіокнопки становить 4% випадків (критичний ризик для пацієнта).
  - *Статус:* 🔴 NON-CONFORMANT.
- **Efficiency (4.1.2):**
  - *Оцінка:* Введення призначення вимагає 8 обов'язкових переходів між екранами і займає в середньому 75 секунд при нормативі екстреної допомоги < 20 секунд.
  - *Статус:* 🟡 PARTIAL.
- **Satisfaction -> Trust & Comfort (4.1.3.2 / 4.1.3.4):**
  - *Оцінка:* Медперсонал відчуває постійний стрес через заплутані діалоги підтвердження; низький рівень довіри до автоматичних підказок.
  - *Статус:* 🟡 PARTIAL.
- **Freedom from risk -> Health and safety risk mitigation (4.1.4.2):**
  - *Оцінка:* Відсутня перевірка несумісності призначеного препарату з наявними алергіями пацієнта у базі (критична загроза життю).
  - *Статус:* 🔴 NON-CONFORMANT.
- **Context coverage -> Context completeness (4.1.5.1):**
  - *Оцінка:* При короткочасному зникненні Wi-Fi у палаті додаток блокує введення замість переходу в автономний режим з кешуванням.
  - *Статус:* 🔴 NON-CONFORMANT.

### Рекомендації щодо покращення:
1. **User error protection (4.2.4.4) ──► Health & Safety (4.1.4.2):** Впровадити обов'язковий automated drug interaction & allergy checker з візуальним алертом високого контрасту при конфлікті ліків.
2. **Operability & Aesthetics (4.2.4.3 / 4.2.4.5) ──► Efficiency (4.1.2):** Переробити UI на 1-Screen Quick Prescribe з великими кнопками типових дозувань (touch targets >= 48x48dp), скоротивши час до 12 секунд.
3. **Fault tolerance (4.2.5.3) ──► Context completeness (4.1.5.1):** Реалізувати offline-first архітектуру на базі локального SQLite/IndexedDB з автоматичною фоновою синхронізацією.
