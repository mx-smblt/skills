## 1. Functional suitability (Функціональна придатність)

Ступінь, до якого продукт або система надає функції, що відповідають заявленим і прихованим (stipulated & implied) потребам при використанні за визначених умов.

### 1.1 Functional completeness (Функціональна повнота)
- **Визначення (4.2.1.1):** Ступінь, до якого набір функцій покриває всі визначені завдання та цілі користувачів.
- **Що перевіряти:**
  - Чи всі користувацькі сценарії (use cases / user stories) реалізовані та описані.
  - Чи немає пропущених обов'язкових бізнес-кроків, станів сутностей або граничних операцій (CRUDL, імпорт/експорт, скасування).
  - Чи відсутні позначки `TBD`/`TBR`/незавершені функціональні блоки.
- **Типові маркери дефектів:**
  - Відсутність обробки обов'язкових бізнес-випадків; відсутність функцій адміністрування, аудиту або керування конфігурацією.
  - Неповне покриття вимог доменного бізнес-процесу.
- **Рекомендовані метрики:**
  - *Functional coverage:* $\frac{\text{Кількість реалізованих функцій}}{\text{Кількість специфікованих функцій}} \times 100\%$.

### 1.2 Functional correctness (Функціональна коректність)
- **Визначення (4.2.1.2):** Ступінь, до якого продукт або система забезпечує правильні результати з потрібним ступенем точності.
- **Що перевіряти:**
  - Точність обчислень, округлення, фінансові/математичні алгоритми.
  - Коректність переходів між станами бізнес-логіки.
  - Валідація вхідних даних та генерація математично й логічно правильних вихідних результатів.
- **Типові маркери дефектів:**
  - Помилки округлення (наприклад, float замість Decimal у грошових транзакціях).
  - Неправильні логічні оператори, відсутність точності в специфікаціях алгоритмів.
- **Рекомендовані метрики:**
  - *Calculation accuracy:* Відсоток розрахунків/операцій, які повертають результат у межах заданої похибки.
  - *Defect density:* Кількість функціональних дефектів на KLOC або на кількість User Stories.

### 1.3 Functional appropriateness (Функціональна доцільність)
- **Визначення (4.2.1.3):** Ступінь, до якого функції сприяють виконанню визначених завдань та цілей (виключаючи зайві та ускладнені кроки).
- **Що перевіряти:**
  - Чи відповідає послідовність дій природному робочому процесу користувача.
  - Чи немає надлишкових, дублюючих або штучно ускладнених функцій.
  - Відповідність принципу «придатності для завдання» (ISO 9241-110).
- **Типові маркери дефектів:**
  - Вимагання від користувача повторного введення даних, які система вже має.
  - Зайві діалогові вікна або ручні переходи для типових рутинних операцій.
- **Рекомендовані метрики:**
  - *Task accomplishment efficiency:* Частка кроків/дій, що безпосередньо створюють цінність, від загальної кількості кроків.

## 2. Performance efficiency (Продуктивність / Ефективність функціонування)

Ступінь продуктивності відносно обсягу ресурсів, використаних за визначених умов.

### 2.1 Time behaviour (Часова поведінка)
- **Визначення (4.2.2.1):** Ступінь, до якого час відгуку, час обробки та пропускна здатність продукту або системи під час виконання функцій відповідають вимогам.
- **Що перевіряти:**
  - Response time (час відгуку UI/API при 95th/99th перцентилях).
  - Latency, Processing time для пакетної або фонової обробки.
  - Throughput (RPS/TPS) за нормальних та пікових умов.
- **Типові маркери дефектів:**
  - Невизначені або розмиті вимоги («система повинна працювати швидко»).
  - Блокуючі синхронні виклики у високонавантажених точках, N+1 query problem.
- **Рекомендовані метрики:**
  - *Response time (P95/P99):* Середній/максимальний час відповіді API (мс/с).
  - *Throughput rate:* Кількість успішно оброблених транзакцій за секунду (TPS).

### 2.2 Resource utilization (Використання ресурсів)
- **Визначення (4.2.2.2):** Ступінь, до якого обсяги та типи ресурсів, що використовуються продуктом під час виконання функцій, відповідають вимогам.
- **Що перевіряти:**
  - CPU, RAM, Disk I/O, Network Bandwidth споживання.
  - Витік пам'яті (memory leaks), неналежне утримання з'єднань з БД (connection pool exhaustion).
  - Енергоефективність (для мобільних та вбудованих систем).
- **Типові маркери дефектів:**
  - Завантаження всього масиву даних у пам'ять замість стрімінгу/пагінації.
  - Відсутність лімітів споживання ресурсів на рівні контейнерів/процесів.
- **Рекомендовані метрики:**
  - *Memory utilization ratio:* $\frac{\text{Використана оперативна пам'ять}}{\text{Виділений ліміт пам'яті}}$.
  - *CPU consumption profile:* Пікове та середнє навантаження на процесор під час виконання операції.

### 2.3 Capacity (Місткість / Пропускна здатність)
- **Визначення (4.2.2.3):** Ступінь, до якого максимальні ліміти параметрів продукту або системи (кількість користувачів, обсяг даних, транзакцій) відповідають вимогам.
- **Що перевіряти:**
  - Максимальна кількість одночасних користувачів (concurrent active users).
  - Граничний розмір БД, максимальний розмір завантажуваного файлу, ліміти черг.
  - Поведінка системи при досягненні 80%, 100% та 120% місткості.
- **Типові маркери дефектів:**
  - Відсутність архітектурного масштабування (scale-up / scale-out); використання 32-бітних лічильників для великих обсягів даних.
  - Відсутність backpressure або rate limiting механізмів.
- **Рекомендовані метрики:**
  - *Transaction capacity saturation point:* Навантаження, при якому виникає деградація SLA або відмова.
  - *Storage growth rate compliance:* Запас місткості сховища відносно прогнозу зростання.

## 3. Compatibility (Сумісність)

Ступінь, до якого продукт, система або компонент може обмінюватися інформацією з іншими продуктами, системами чи компонентами та/або виконувати свої функції, розділяючи спільне апаратне або програмне середовище.

### 3.1 Co-existence (Співіснування)
- **Визначення (4.2.3.1):** Ступінь, до якого продукт може ефективно виконувати свої функції, розділяючи спільне середовище та ресурси з іншими продуктами без негативного впливу на будь-який інший продукт.
- **Що перевіряти:**
  - Конфлікти портів, спільних бібліотек (DLL hell), змінних оточення, тимчасових директорій.
  - Конфлікти блокування спільних файлів, ресурсів ОС або таблиць баз даних.
  - Ізоляція середовищ (контейнеризація, namespace).
- **Типові маркери дефектів:**
  - Захоплення глобальних ресурсів без звільнення; жорстко закодовані статичні порти чи шляхи.
  - Відсутність ізоляції процесів, взаємне блокування (deadlocks) сторонніх процесів.
- **Рекомендовані метрики:**
  - *Co-existence degradation rate:* Рівень зниження продуктивності сусідніх сервісів при роботі продукту.

### 3.2 Interoperability (Взаємодієздатність / Інтероперабельність)
- **Визначення (4.2.3.2):** Ступінь, до якого дві або більше систем, продуктів або компонентів можуть обмінюватися інформацією та використовувати обміняну інформацію.
- **Що перевіряти:**
  - Використання відкритих стандартів та протоколів (REST, gRPC, OpenAPI/Swagger, JSON/Protobuf, ISO 20022).
  - Зворотна сумісність схем даних (schema evolution, API versioning).
  - Семантична сумісність (однакове тлумачення полів, кодів та типів даних).
- **Типові маркери дефектів:**
  - Власні закриті бінарні формати без специфікації; відсутність валідації схем.
  - Несумісні версії API без підтримки версіонування.
- **Рекомендовані метрики:**
  - *Data exchange success rate:* Відсоток успішних інтеграційних операцій без трансформаційних помилок.
  - *Standard format compliance:* Відсоток інтерфейсів, які відповідають визначеним міжнародним або галузевим специфікаціям.

## 4. Usability (Зручність використання)

Ступінь, до якого продукт або система може використовуватися визначеними користувачами для досягнення визначених цілей з результативністю, ефективністю та задоволеністю у визначеному контексті використання.

### 4.1 Appropriateness recognizability (Впізнаваність доцільності)
- **Визначення (4.2.4.1):** Ступінь, до якого користувачі можуть розпізнати, чи підходить продукт або система для їхніх потреб (на основі першого враження, документації, лендингу).
- **Що перевіряти:**
  - Зрозумілість опису можливостей системи, наявність туторіалів, демо-версій, прикладів використання.
  - Чітке позиціонування призначення системи в інтерфейсі (onboarding, home screen).
- **Типові маркери дефектів:**
  - Відсутність інструкцій швидкого старту; технічний жаргон на початкових екранах без пояснення призначення.
- **Рекомендовані метрики:**
  - *First-time user recognition rate:* Відсоток нових користувачів, які правильно визначають призначення продукту за перші 3 хвилини.

### 4.2 Learnability (Навчаність)
- **Визначення (4.2.4.2):** Ступінь, до якого продукт або система дозволяє користувачам досягти цілей вивчення використання системи з результативністю, ефективністю, свободою від ризиків та задоволеністю.
- **Що перевіряти:**
  - Наявність контекстної довідки, tooltips, guided tours.
  - Передбачуваність поведінки елементів UI, інтуїтивність ментальної моделі.
  - Час, необхідний для виконання першої успішної операції новачком.
- **Типові маркери дефектів:**
  - Неконсистентна поведінка однакових кнопок на різних екранах; відсутність підказок до складних полів.
- **Рекомендовані метрики:**
  - *Time to proficiency:* Середній час/кількість спроб до досягнення автономного виконання базових завдань без допомоги.

### 4.3 Operability (Керованість / Простота використання)
- **Визначення (4.2.4.3):** Ступінь, до якого продукт або система має атрибути, які роблять його легким в експлуатації та управлінні.
- **Що перевіряти:**
  - Зручність навігації, підтримка гарячих клавіш, налаштовуваність (customization).
  - Співвідношення кліків/дій для виконання частих сценаріїв.
  - Контрольованість: можливість скасувати дію (Undo/Redo), паузи, підтвердження.
- **Типові маркери дефектів:**
  - Неможливість керування з клавіатури; відсутність пошуку/фільтрів у великих списках; неможливість скасування випадкової дії.
- **Рекомендовані метрики:**
  - *Operational step reduction:* Кількість дій користувача для виконання типового бізнес-сценарію.

### 4.4 User error protection (Захист від помилок користувача)
- **Визначення (4.2.4.4):** Ступінь, до якого система захищає користувачів від здійснення помилок.
- **Що перевіряти:**
  - Попередня валідація вводу (input masks, inline validation, datepickers).
  - Попередження перед незворотними операціями (видалення, фінансові проводки).
  - Зрозумілі повідомлення про помилки з чіткою інструкцією, як їх виправити.
- **Типові маркери дефектів:**
  - Загальні помилки типу "Error 500: An error occurred" без пояснення причини та кроків вирішення; стирання введених даних форми при помилці валідації.
- **Рекомендовані метрики:**
  - *User error rate:* Кількість помилок користувача на виконане завдання.
  - *Error recovery rate:* Відсоток випадків, коли користувач самостійно виправив помилку за допомогою підказки системи.

### 4.5 User interface aesthetics (Естетика інтерфейсу користувача)
- **Визначення (4.2.4.5):** Ступінь, до якого інтерфейс забезпечує приємну та задовільну взаємодію для користувача (дизайн, типографіка, колірна гама).
- **Що перевіряти:**
  - Візуальна ієрархія, контрастність, баланс білого простору, узгодженість Design System.
  - Плавність анімацій та відсутність візуального шуму.
- **Типові маркери дефектів:**
  - Різні шрифти та стилі кнопок в одному додатку; незбалансовані, занадто яскраві кольори.
- **Рекомендовані метрики:**
  - *Visual consistency score:* Відсоток екранів/компонентів, що строго відповідають Design System.

### 4.6 Accessibility (Доступність)
- **Визначення (4.2.4.6):** Ступінь, до якого продукт або система може використовуватися людьми з найширшим діапазоном характеристик і можливостей (включаючи людей з інвалідністю та віковими обмеженнями).
- **Що перевіряти:**
  - Відповідність стандарту WCAG 2.1 / 2.2 (рівні A, AA, AAA).
  - Підтримка Screen Readers (ARIA-мітки, семантичний HTML/компоненти).
  - Контрастність тексту (мінімум 4.5:1 для звичайного тексту), підтримка масштабування шрифтів без зламу верстки.
- **Типові маркери дефектів:**
  - Зображення без `alt`-атрибутів; використання виключно кольору для позначення статусу помилки/успіху; неможливість навігації лише клавіатурою (Tab-focus trap).
- **Рекомендовані метрики:**
  - *WCAG Conformance Rate:* Відсоток критеріїв WCAG AA, які успішно виконані.

## 5. Reliability (Надійність)

Ступінь, до якого система, продукт або компонент виконує визначені функції за визначених умов протягом визначеного періоду часу.

### 5.1 Maturity (Зрілість)
- **Визначення (4.2.5.1):** Ступінь, до якого система, продукт або компонент задовольняє потреби в надійності за нормальних умов експлуатації.
- **Що перевіряти:**
  - Частота виникнення збоїв під час штатної роботи (MTBF — Mean Time Between Failures).
  - Стабільність релізів, відсутність регресійних дефектів.
- **Типові маркери дефектів:**
  - Високий рівень збоїв після релізу; «плаваючі» баги (Heisenbugs), race conditions.
- **Рекомендовані метрики:**
  - *MTBF (Mean Time Between Failures):* Середній час між збоями системи.
  - *Failure rate:* Кількість інцидентів на 1000 годин роботи.

### 5.2 Availability (Готовність / Доступність)
- **Визначення (4.2.5.2):** Ступінь, до якого система, продукт або компонент перебуває в працездатному та доступному для використання стані, коли це потрібно.
- **Що перевіряти:**
  - Відсоток uptime (SLA 99.9%, 99.99%, 99.999%).
  - Планові та непланові простої (scheduled & unscheduled downtime).
  - Наявність резервування (redundancy, high availability clusters, multi-region failover).
- **Типові маркери дефектів:**
  - Єдина точка відмови (Single Point of Failure — SPOF) в інфраструктурі чи архітектурі.
  - Необхідність зупинки всієї системи для оновлення без підтримки Zero-Downtime Deployment (Blue-Green / Canary).
- **Рекомендовані метрики:**
  - *System availability:* $\frac{\text{Uptime}}{\text{Uptime} + \text{Downtime}} \times 100\%$.

### 5.3 Fault tolerance (Відмовостійкість)
- **Визначення (4.2.5.3):** Ступінь, до якого система функціонує за призначенням, незважаючи на наявність апаратних або програмних збоїв.
- **Що перевіряти:**
  - Патерни стійкості: Circuit Breaker, Retry with Exponential Backoff, Bulkhead, Fallbacks, Graceful Degradation.
  - Обробка тайм-аутів та збоїв зовнішніх сервісів.
- **Типові маркери дефектів:**
  - Каскадні падіння (cascading failures): збій одного мікросервісу кладе всю систему.
  - Відсутність graceful degradation (наприклад, система повністю падає, якщо відключився сервіс рекомендацій).
- **Рекомендовані метрики:**
  - *Fault containment ratio:* Частка збоїв компонентів, які були ізольовані без порушення роботи основних функцій системи.

### 5.4 Recoverability (Відновлюваність)
- **Визначення (4.2.5.4):** Ступінь, до якого у разі переривання або збою продукт може відновити безпосередньо уражені дані та повернутися до бажаного стану.
- **Що перевіряти:**
  - MTTR (Mean Time To Recover / Repair).
  - RPO (Recovery Point Objective) та RTO (Recovery Time Objective).
  - Наявність автоматичного відновлення (auto-restart, self-healing), регулярність перевірки бекапів (Disaster Recovery drills).
- **Типові маркери дефектів:**
  - Відсутність транзакційної цілісності (розподілені транзакції без SAGA/2PC залишають дані в розсинхронізованому стані).
  - Бекапи створюються, але ніколи не тестувалося їх відновлення.
- **Рекомендовані метрики:**
  - *MTTR:* Середній час відновлення системи після аварії.
  - *Data loss on recovery (RPO actual vs target):* Обсяг втрачених даних при збої.

## 6. Security (Безпека / Захищеність)

Ступінь, до якого продукт або система захищає інформацію та дані, так що особи або інші системи мають ступінь доступу до даних, відповідний їхнім типам і рівням авторизації.

### 6.1 Confidentiality (Конфіденційність)
- **Визначення (4.2.6.1):** Ступінь, до якого система гарантує, що дані доступні лише тим, хто має авторизований доступ.
- **Що перевіряти:**
  - Шифрування даних у стані спокою (Data at Rest — AES-256) та під час передачі (Data in Transit — TLS 1.3).
  - Маскування персональних даних (PII), токенізація, управління секретами (Secrets Manager / Vault).
  - Захист від витоку даних через логи або повідомлення про помилки.
- **Типові маркери дефектів:**
  - Секрети/паролі у відкритому коді; логування токенів, паролів або номерів кредитних карток.
  - Відсутність шифрування на рівні бази даних або сховища дисків.
- **Рекомендовані метрики:**
  - *Encryption coverage:* Відсоток конфіденційних каналів зв'язку та сховищ із діючим криптографічним захистом (цільове: 100%).

### 6.2 Integrity (Цілісність)
- **Визначення (4.2.6.2):** Ступінь, до якого система запобігає несанкціонованому доступу до комп'ютерних програм чи даних або їх модифікації.
- **Що перевіряти:**
  - Захист від ін'єкцій (SQL Injection, XSS, CSRF, RCE, Command Injection).
  - Контроль цілісності файлів та пакетів (HMAC, цифрові підписи, Checksums).
  - Рольова модель доступу (RBAC / ABAC) та валідація прав на кожну мутуючу дію на бекенді.
- **Типові маркери дефектів:**
  - Відсутність авторизації на рівні об'єкта (IDOR / BOLA); виконання сирих SQL-запитів з конкатенацією рядків.
  - Відсутність перевірки валідності вхідних JSON/XML payload.
- **Рекомендовані метрики:**
  - *Vulnerability density:* Кількість вразливостей категорій OWASP Top-10 / CWE на кодову базу.

### 6.3 Non-repudiation (Невідмовність)
- **Визначення (4.2.6.3):** Ступінь, до якого можна довести, що дії або події мали місце, так що ці події або дії не можуть бути спростовані пізніше.
- **Що перевіряти:**
  - Використання кваліфікованого електронного підпису (Digital Signatures) для юридично та фінансово значущих дій.
  - Незмінність журналів аудиту (WORM storage, append-only logs, cryptographic hashing chains).
- **Типові маркери дефектів:**
  - Можливість модифікації або видалення записів журналу транзакцій користувачем або адміністратором.
  - Відсутність фіксації контексту операції (IP, timestamp, сертифікат) при підписанні.
- **Рекомендовані метрики:**
  - *Unsigned critical transactions ratio:* Відсоток критичних бізнес-транзакцій без цифрового доказу невідмовності (має бути 0%).

### 6.4 Accountability (Підзвітність / Простежуваність дій)
- **Визначення (4.2.6.4):** Ступінь, до якого дії сутності можуть бути однозначно простежені до цієї конкретної сутності.
- **Що перевіряти:**
  - Повний аудит-лог (Audit Trail): хто, коли, з якого IP, яку сутність переглядав/змінював/видалив.
  - Заборона використання спільних або системних акаунтів без персональної ідентифікації.
  - Кореляційні ідентифікатори (Correlation ID / Trace ID) для наскрізного аудиту.
- **Типові маркери дефектів:**
  - Спільний логін `admin` для кількох операторів; відсутність логів доступу до чутливих даних (Read operations).
- **Рекомендовані метрики:**
  - *Audit logging coverage:* Відсоток безпекових та бізнес-подій, що фіксуються в незмінному аудит-журналі.

### 6.5 Authenticity (Автентичність)
- **Визначення (4.2.6.5):** Ступінь, до якого ідентичність суб'єкта або ресурсу може бути доведена як справжня.
- **Що перевіряти:**
  - Багатофакторна автентифікація (MFA / 2FA), надійні алгоритми хешування паролів (Argon2, bcrypt, PBKDF2).
  - Взаємна автентифікація сервісів (mTLS), перевірка валідності JWT (підпис, термін дії, audience, issuer).
- **Типові маркери дефектів:**
  - Використання застарілих алгоритмів хешування (MD5, SHA-1); відсутність перевірки підпису токена; слабка політика паролів без MFA.
- **Рекомендовані метрики:**
  - *Authentication robustness index:* Відсоток точок входу, захищених стійкою автентифікацією (MFA/mTLS).

## 7. Maintainability (Супроводжуваність / Підтримуваність)

Ступінь результативності та ефективності, з якими продукт або система може бути модифікована розробниками та супроводжуючим персоналом.

### 7.1 Modularity (Модульність)
- **Визначення (4.2.7.1):** Ступінь, до якого система складається з дискретних компонентів, таких що зміна одного компонента має мінімальний вплив на інші компоненти.
- **Що перевіряти:**
  - Дотримання високого Cohesion (зв'язності всередині модуля) та низького Coupling (зачеплення між модулями).
  - Архітектурні межі (Bounded Contexts у DDD, Clean Architecture, Onion Architecture).
  - Відсутність циклічних залежностей між пакетами/модулями.
- **Типові маркери дефектів:**
  - Монолітні класи-"боги" (God Object), спагеті-код, циклічні імпорти між модулями.
- **Рекомендовані метрики:**
  - *Afferent/Efferent coupling (Ca/Ce), Instability (I):* $I = \frac{Ce}{Ca + Ce}$.
  - *Cyclic dependencies count:* Кількість циклічних зв'язків (має бути 0).

### 7.2 Reusability (Повторна використовуваність)
- **Визначення (4.2.7.2):** Ступінь, до якого актив може використовуватися більше ніж в одній системі або для створення інших активів.
- **Що перевіряти:**
  - Наявність спільних бібліотек, SDK, UI компонентів (Design System).
  - Відсутність жорсткої прив'язки доменного коду до конкретного фреймворку або зовнішнього оточення.
  - Параметризація та конфігурованість компонентів.
- **Типові маркери дефектів:**
  - Copy-paste програмування, дублювання коду (Code Duplication > 5%).
- **Рекомендовані метрики:**
  - *Code duplication ratio:* Відсоток дубльованих рядків або блоків коду.
  - *Shared component utilization:* Відсоток проєктів/модулів, які використовують спільну базову бібліотеку.

### 7.3 Analysability (Аналізованість)
- **Визначення (4.2.7.3):** Ступінь результативності та ефективності, з якими можна оцінити вплив запланованих змін, діагностувати недоліки або причини збоїв, або визначити частини для модифікації.
- **Що перевіряти:**
  - Структуроване логування (JSON logs, log levels INFO/WARN/ERROR), Distributed Tracing (OpenTelemetry).
  - Метрики стану (Prometheus/Grafana), Health Check endpoints (`/health/live`, `/health/ready`).
  - Читабельність коду, коментарі архітектурних рішень (ADR).
- **Типові маркери дефектів:**
  - Порожні catch-блоки `catch (Exception e) {}`; неінформативні логи без контексту; відсутність трейсингу в розподілених сервісах.
- **Рекомендовані метрики:**
  - *Mean Time to Diagnose (MTTD):* Середній час на виявлення першопричини інциденту (Root Cause Analysis).
  - *Cyclomatic complexity (McCabe):* Середня та максимальна цикломатична складність методів (рекомендовано <= 10-15).

### 7.4 Modifiability (Змінюваність / Модифіковність)
- **Визначення (4.2.7.4):** Ступінь, до якого продукт або система може бути результативно та ефективно модифікована без внесення дефектів або погіршення наявної якості.
- **Що перевіряти:**
  - Дотримання принципів SOLID, DRY, KISS, YAGNI.
  - Наявність автоматизованого CI/CD пайплайну з перевіркою регресій.
  - Конфігурація винесена окремо від коду (12-Factor App methodology).
- **Типові маркери дефектів:**
  - Hardcoded конфігурація в коді; зміна однієї фічі призводить до падіння непов'язаних модулів (Shotgun Surgery).
- **Рекомендовані метрики:**
  - *Change failure rate (CFR):* Відсоток змін, які призводять до дефектів або вимагають hotfix/rollback.
  - *Lead time for changes:* Час від створення коду до його безпечного викачування в production.

### 7.5 Testability (Тестованість)
- **Визначення (4.2.7.5):** Ступінь результативності та ефективності, з якими можуть бути встановлені критерії тестування для системи та виконані тести для визначення досягнення цих критеріїв.
- **Що перевіряти:**
  - Впровадження залежностей (Dependency Injection / Inversion of Control), ізоляція побічних ефектів.
  - Наявність тестових дублерів (Mocks, Stubs, Testcontainers), можливість тестування окремих компонентів ізольовано.
  - Рівень покриття тестами (Unit, Integration, E2E, Contract tests).
- **Типові маркери дефектів:**
  - Статичні синглтони з внутрішнім станом, які неможливо замінити в тестах; пряме звернення до БД всередині бізнес-класів без інтерфейсів.
- **Рекомендовані метрики:**
  - *Code test coverage (Line / Branch):* Покриття коду автотестами (рекомендовано > 80% line, > 70% branch).
  - *Test execution speed:* Загальний час прогону набору unit та integration тестів.

## 8. Portability (Мобільність / Переносність)

Ступінь результативності та ефективності, з якими система, продукт або компонент може бути перенесений з одного апаратного, програмного чи операційного середовища в інше.

### 8.1 Adaptability (Адаптованість)
- **Визначення (4.2.8.1):** Ступінь, до якого продукт або система може ефективно адаптуватися до різних або мінливих апаратних, програмних чи інших робочих середовищ (включає масштабованість внутрішньої місткості, локалізацію, різні ОС/браузери).
- **Що перевіряти:**
  - Кросплатформність (робота на Linux, Windows, macOS; підтримка сучасних браузерів Chrome, Firefox, Safari, Edge).
  - Інтернаціоналізація та локалізація (i18n / l10n: підтримка UTF-8, часових поясів UTC, різних мов, валют).
  - Адаптивний UI (Responsive Web Design — десктоп, планшет, мобільний).
- **Типові маркери дефектів:**
  - Залежність від специфічних системних викликів однієї ОС (наприклад, hardcoded роздільники шляхів `\` замість `path.join`); жорстко зашиті рядки тексту в коді без i18n ключів.
- **Рекомендовані метрики:**
  - *Platform compatibility coverage:* Кількість підтримуваних цільових середовищ без необхідності зміни коду.

### 8.2 Installability (Встановлюваність / Інстальованість)
- **Визначення (4.2.8.2):** Ступінь результативності та ефективності, з якими продукт може бути успішно встановлений та/або деінстальований у визначеному середовищі.
- **Що перевіряти:**
  - Автоматизація розгортання (Docker, Helm charts, Terraform, Ansible, скрипти інсталяції).
  - Чіткість документації з встановлення, перевірка попередніх вимог (prerequisites check).
  - Чистота деінсталяції (відсутність залишкового сміття, звільнення ресурсів).
- **Типові маркери дефектів:**
  - Ручний процес встановлення з десятками недокументованих кроків; відсутність перевірки сумісності версій під час старту інсталятора.
- **Рекомендовані метрики:**
  - *Installation success rate on first attempt:* Відсоток успішних установок без помилок з першої спроби.
  - *Time to install:* Час повного розгортання системи в новому середовищі.

### 8.3 Replaceability (Замінність)
- **Визначення (4.2.8.3):** Ступінь, до якого продукт може замінити інший визначений програмний продукт для тієї самої мети в тому самому середовищі (зменшення vendor lock-in).
- **Що перевіряти:**
  - Сумісність форматів даних (імпорт/експорт у відкриті формати CSV, JSON, XML, SQL dumps, Parquet).
  - Сумісність API (дотримання стандартних специфікацій протоколів, наприклад S3-compatible API, OIDC).
  - Міграційні інструменти та скрипти переносу даних з попередніх систем.
- **Типові маркери дефектів:**
  - Закриті пропрієтарні формати даних без можливості експорту (Vendor lock-in); відсутність документації та інструментів міграції.
- **Рекомендовані метрики:**
  - *Data migration effort / completeness:* Відсоток успішно перенесених сутностей та налаштувань без ручної конвертації.
